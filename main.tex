\begin{abstract}
Modern GPUs are increasingly shared across multiple concurrent workloads, from latency-sensitive inference jobs to throughput-oriented training tasks. Because GPUs are fundamentally non-preemptive (a kernel cannot be interrupted once it starts), scheduling decisions have an outsized impact on job waiting times, fairness, and overall throughput.

In this project, we study the tradeoffs among latency, fairness, and throughput in non-preemptive shared GPU scheduling. We use ISCAS-85 circuit benchmarks to generate realistic task graphs with diverse dependency structures. Each circuit gate becomes a task executed by a synthetic CUDA kernel, allowing us to control computational characteristics while preserving realistic dependencies. We implement and evaluate six scheduling policies: FIFO, priority-based, and four dependency-aware variants (HighFanout, CriticalPath, LevelAware, Hybrid) across both sequential and concurrent execution modes. Using the LSIM framework with real GPU execution, we measure completion time, waiting time, throughput, GPU utilization, and Jain's fairness index across balanced and imbalanced workload configurations with varying batch sizes (32, 128, 512).

Our results demonstrate clear tradeoffs: balanced workloads achieve near-optimal fairness (~0.98) across all schedulers, while imbalanced workloads reveal significant scheduler-dependent fairness degradation (0.67--0.81). Priority-based scheduling minimizes latency for high-priority tasks but can cause severe starvation (up to 2.5M$\times$ slowdown for low-priority workloads). Dependency-aware schedulers like CriticalPath and LevelAware improve overall makespan but may sacrifice individual task responsiveness. Most significantly, concurrent execution improves GPU utilization from 10--25\% to 65--99\% compared to sequential batch dispatch, directly addressing the CPU launch overhead bottleneck. These findings provide concrete guidance for selecting appropriate scheduling policies based on workload characteristics and system priorities in shared GPU environments.
\end{abstract}

\section{Introduction}

Graphics Processing Units (GPUs) have evolved from dedicated graphics accelerators into general-purpose parallel computing platforms. Modern GPUs power diverse workloads ranging from latency-sensitive real-time graphics and video processing to throughput-oriented machine learning training and scientific computing. As GPU computing becomes ubiquitous, multiple applications increasingly share the same GPU hardware concurrently, creating complex resource contention scenarios.

A fundamental constraint shapes GPU resource management: GPUs are \emph{non-preemptive}. Once a kernel begins execution, it cannot be interrupted until completion. This differs markedly from CPU scheduling, where the operating system can preempt running processes at any time to enforce priorities or fairness. On GPUs, scheduling decisions occur only at kernel boundaries, and a poorly-timed long-running kernel can block all other pending work regardless of priority. This non-preemptive nature amplifies the impact of scheduling policy on system-wide performance metrics including job latency, fairness across workloads, and overall throughput.

Prior work has recognized the importance of GPU scheduling. TimeGraph~\cite{kato2011timegraph} introduced priority-based scheduling and resource reservation mechanisms at the device driver level, demonstrating that GPU applications can be protected from interference in multi-tasking environments. However, existing work primarily focuses on \emph{enabling} prioritization and isolation rather than systematically characterizing the \emph{tradeoffs} inherent in different scheduling policies. When should a scheduler prioritize low-latency response for high-priority tasks versus maximizing overall throughput? How do dependency-aware policies that exploit task graph structure affect fairness? What is the cost of sequential versus concurrent task dispatch in terms of GPU utilization?

In this project, we address these questions through comprehensive empirical evaluation. We implement six GPU scheduling policies spanning three categories: FIFO baseline, priority-based scheduling, and four dependency-aware variants (HighFanout, CriticalPath, LevelAware, and Hybrid). Each scheduler is evaluated under both sequential batch dispatch and concurrent multi-stream execution. We execute on real GPU hardware using ISCAS-85 circuit benchmarks as a source of realistic task graphs. Each gate in a circuit corresponds to one task executed by a synthetic CUDA kernel, preserving the circuit's dependency structure while allowing control over kernel computational behavior. Our evaluation measures latency (completion time, waiting time), throughput (tasks per second), GPU utilization, and fairness (Jain's index) across balanced and imbalanced workload configurations.

Our key findings quantify fundamental tradeoffs in GPU scheduling:

\begin{itemize}
\item \textbf{Fairness degrades with workload imbalance}: While all schedulers achieve near-perfect fairness (Jain's index $\sim$0.98) on balanced workloads, imbalanced workloads expose scheduler-specific weaknesses, with fairness dropping to 0.67--0.81.

\item \textbf{Priority scheduling trades fairness for latency}: Priority-based policies minimize latency for high-priority tasks but can cause extreme starvation, with low-priority workloads experiencing up to 2.5M$\times$ slowdown.

\item \textbf{Dependency-aware scheduling improves makespan}: Schedulers that exploit task graph structure (CriticalPath, LevelAware) reduce overall completion time but may delay individual task responsiveness.

\item \textbf{Concurrent dispatch is essential for utilization}: Sequential batch dispatch achieves only 10--25\% GPU utilization due to CPU launch overhead, while concurrent multi-stream execution reaches 65--99\% utilization.
\end{itemize}

\section{Background}
\label{sec:background}

\subsection{GPU Execution Model}

Modern GPUs expose a massively parallel execution model through programming frameworks like CUDA. A GPU program is organized as a \emph{kernel}, which executes across thousands of lightweight threads grouped into blocks. The GPU schedules blocks onto streaming multiprocessors (SMs), and threads within a block execute in lockstep groups called warps.

A critical characteristic of GPU execution is its \emph{non-preemptive} nature. Once a kernel begins execution on the GPU, it runs to completion without interruption. The GPU hardware scheduler cannot pause a running kernel to execute a higher-priority task. This contrasts sharply with CPU scheduling, where the operating system timer can preempt any process to enforce priorities or fair sharing. On GPUs, scheduling decisions occur only at kernel boundaries, when one kernel completes and the next is launched.

GPUs execute asynchronously with respect to the CPU. The CPU issues GPU commands (kernel launches, memory transfers) to a queue, and the GPU processes these commands independently while the CPU continues executing. This asynchrony enables overlap between CPU and GPU work, but it also complicates scheduling: the CPU-side scheduler must predict GPU execution costs and coordinate task dispatch without real-time feedback on GPU state.

\subsection{Task Graphs and Dependencies}

Many GPU workloads exhibit dependencies between tasks. A \emph{task graph} models these dependencies as a directed acyclic graph (DAG) where nodes represent computational tasks (kernels) and edges represent precedence constraints. A task can execute only after all its predecessors have completed.

Task graphs arise naturally in applications like logic simulation, circuit timing analysis, and dataflow computation. For example, in digital circuit simulation, gate outputs depend on their input signals, creating a dependency graph that mirrors the circuit topology. The structure of the task graph profoundly affects scheduling opportunities: tasks on the critical path determine minimum makespan, while tasks with high fan-out expose parallelism.

\subsection{Scheduling Challenges}

GPU scheduling must navigate several competing objectives:

\textbf{Latency:} High-priority or latency-sensitive tasks should complete quickly. Priority scheduling can achieve low latency for important tasks by always dispatching them first.

\textbf{Throughput:} The system should maximize total work completed per unit time. Batching tasks and minimizing idle time improve throughput.

\textbf{Fairness:} Competing workloads should receive equitable GPU time. Jain's fairness index~\cite{jain1984quantitative} quantifies fairness as:
\[
J = \frac{(\sum_{i=1}^{n} x_i)^2}{n \sum_{i=1}^{n} x_i^2}
\]
where $x_i$ is the throughput (or inverse slowdown) of workload $i$. Perfect fairness yields $J=1$, while extreme unfairness approaches $J=1/n$.

\textbf{Utilization:} The GPU should remain busy executing useful work. CPU launch overhead can cause idle time between kernels, reducing utilization.

The non-preemptive constraint creates fundamental tradeoffs. A long-running low-priority kernel blocks all subsequent work, harming latency. Aggressive batching improves throughput but delays individual task response. Dependency-aware scheduling that prioritizes critical-path tasks may starve other workloads.

\subsection{Sequential vs. Concurrent Dispatch}

GPU kernels can be dispatched in two modes:

\textbf{Sequential dispatch} launches one batch of tasks, synchronizes to wait for completion, then launches the next batch. This approach is simple but suffers from CPU launch overhead: the GPU sits idle while the CPU prepares the next batch.

\textbf{Concurrent dispatch} uses CUDA streams to launch multiple independent kernels simultaneously. The GPU scheduler can overlap execution of kernels from different streams, improving utilization. However, concurrent dispatch requires careful management of dependencies and resource allocation to avoid deadlock or contention.


\section{Related Work}
\label{sec:relatedwork}

\subsection{GPU Scheduling Systems}

TimeGraph~\cite{kato2011timegraph} pioneered priority-based GPU scheduling at the device driver level. It introduced an event-driven scheduler that uses GPU-to-CPU interrupts to dispatch tasks based on priority, along with resource reservation mechanisms to prevent low-priority tasks from exhausting GPU time. TimeGraph demonstrated that important GPU applications can be protected from interference in multi-tasking environments, with overheads limited to 4--10\%. However, TimeGraph focuses on \emph{enabling} prioritization and isolation rather than systematically measuring the tradeoffs between priority scheduling, fairness, and throughput across different workload characteristics.

The Graphics Engine Resource Manager (GERM)~\cite{bautin2008germ} takes a fairness-first approach, aiming to provide fair GPU resource allocation among competing applications. GERM uses a tick-driven scheduler that polls GPU state periodically to enforce fairness. While GERM successfully achieves fair sharing, it does not address scenarios where certain applications require priority treatment for latency-sensitive workloads. Additionally, the tick-driven model can suffer from responsiveness issues when many GPU commands arrive in short intervals.

Our work differs from both TimeGraph and GERM in focus and methodology. Rather than proposing a new scheduling mechanism, we systematically evaluate multiple scheduling policies (FIFO, priority-based, dependency-aware) to quantify the inherent tradeoffs. We measure how fairness degrades under priority scheduling, how dependency-aware policies affect individual task latency, and how concurrent versus sequential dispatch impacts utilization. This empirical analysis provides concrete guidance for selecting appropriate policies based on workload requirements.

\subsection{GPU Resource Management}

Gdev~\cite{kato2012gdev} addresses GPU resource management by moving the GPU runtime into the operating system kernel. This enables the OS to manage GPU resources with the same abstractions used for CPU scheduling, including memory virtualization and application isolation through virtual GPUs. While Gdev provides a foundation for OS-level GPU management, the scheduling policies themselves remain an open question that our work addresses.

\subsection{GPU Performance Analysis}

Dublish et al.~\cite{dublish2017bandwidth} analyze bandwidth bottlenecks across the GPU memory hierarchy, demonstrating that L2 cache delays often dominate over DRAM bandwidth as the primary performance limiter. This finding motivates our attention to GPU utilization: inefficient scheduling can leave the GPU idle, wasting both compute and memory bandwidth. Our observation that sequential dispatch achieves only 10--25\% utilization while concurrent dispatch reaches 65--99\% aligns with the importance of keeping the GPU memory hierarchy busy to amortize access latencies.

\subsection{Task Graph Scheduling}

Dependency-aware scheduling for task graphs has been studied extensively in the context of distributed systems and multi-core CPUs. Classic algorithms like critical path scheduling and list scheduling aim to minimize makespan by prioritizing tasks on the longest dependency chain. Our dependency-aware schedulers (CriticalPath, LevelAware, HighFanout) adapt these ideas to the GPU context, where non-preemptive execution and asynchronous dispatch create unique constraints. Our evaluation shows that while these policies improve overall makespan, they can increase individual task latency compared to simpler FIFO scheduling, a tradeoff not well-characterized in prior GPU scheduling work.

\section{Methodology}
\label{sec:methodology}

\subsection{System Overview}

We build our GPU scheduling testbed on the LSIM framework~\cite{lsim}, which provides infrastructure for parsing circuit netlists. LSIM parses ISCAS-85 benchmarks and constructs task graphs where each gate becomes a task node with dependencies reflecting circuit topology. We extend LSIM with multiple scheduling policies and execution modes, replacing its default level-based scheduler with our implementations.

Our system consists of three main components: (1) a circuit parser that constructs task graphs from benchmark netlists, (2) scheduler implementations that determine task execution order, and (3) execution runners that dispatch tasks to the GPU in either sequential or concurrent mode. Each task executes as a synthetic CUDA kernel. Rather than performing actual gate simulation, these kernels emulate three workload types—compute-bound, memory-bound, and latency-sensitive—stressing different GPU resources. This approach preserves realistic task graph structures from real circuits while providing controlled, reproducible kernel behavior for scheduler evaluation.

\subsection{Workload Characterization}

We define six workload groups from ISCAS-85 circuits to create diverse scheduling scenarios:

\textbf{Balanced workloads} (2 groups): Each group runs three circuits of similar size concurrently, creating relatively uniform resource demands. These workloads test scheduler behavior under symmetric competition.

\textbf{Imbalanced workloads} (4 groups): Each group mixes circuits of vastly different sizes (e.g., c17 with 11 gates alongside c7552 with 1857 gates). These workloads stress-test fairness: will small circuits starve while large ones dominate, or will the scheduler equitably share GPU time?

Each circuit generates a task graph with varying structural properties:
\begin{itemize}
\item \textbf{Depth}: The length of the longest dependency chain (critical path)
\item \textbf{Width}: The maximum number of tasks ready to execute concurrently
\item \textbf{Fan-out}: The number of dependent tasks per gate
\end{itemize}

We model three kernel types to emulate different computational characteristics:
\begin{itemize}
\item \textbf{Compute-bound}: Kernels dominated by arithmetic operations
\item \textbf{Memory-bound}: Kernels limited by memory bandwidth
\item \textbf{Latency-sensitive}: Kernels requiring rapid response
\end{itemize}

Workloads arrive with staggered timing (10ms gaps) to simulate realistic concurrent submission rather than synchronous batch arrival.

\subsection{Scheduler Implementations}

We implement six scheduling policies:

\textbf{FIFO}: Tasks are enqueued as dependencies are satisfied and executed in strict arrival order. This baseline provides predictable response times but ignores both priority and dependency structure.

\textbf{Priority}: Each workload is assigned a static priority (0--2, lower is higher priority). The scheduler always dispatches the highest-priority ready task. This policy minimizes latency for important workloads but risks starvation of low-priority tasks.

\textbf{HighFanout}: Prioritizes tasks with the most dependent downstream tasks, aiming to unblock parallelism early. This policy exploits task graph width.

\textbf{CriticalPath}: Prioritizes tasks on the longest remaining dependency chain. By focusing on the critical path, this policy minimizes overall makespan but may delay tasks off the critical path.

\textbf{LevelAware}: Groups tasks by dependency level (distance from inputs) and prioritizes deeper tasks. This balances depth and width considerations.

\textbf{Hybrid}: Combines priority with dependency-awareness, using priority as the primary criterion and critical path length as a tiebreaker.

Each scheduler maintains a ready queue of tasks whose dependencies are satisfied. At each scheduling point (when a batch completes or a kernel finishes in concurrent mode), the scheduler selects up to \texttt{batch\_size} tasks according to its policy and dispatches them to the GPU.

\subsection{Execution Modes}

\textbf{Sequential execution}: The system launches a batch of up to \texttt{batch\_size} ready tasks, synchronizes with \texttt{cudaDeviceSynchronize()} to wait for completion, updates dependent tasks, and repeats. This mode minimizes complexity but suffers from CPU launch overhead: the GPU idles while the CPU prepares the next batch.

\textbf{Concurrent execution}: The system uses CUDA streams to launch multiple independent tasks simultaneously without explicit synchronization between batches. Dependencies are tracked asynchronously, and new tasks are dispatched as soon as their predecessors complete. This mode improves GPU utilization by overlapping kernel execution with CPU-side scheduling decisions.

\subsection{Experimental Configuration}

We vary two key parameters:

\textbf{Batch size}: \{32, 128, 512\} tasks per dispatch. Larger batches amortize launch overhead but reduce scheduling flexibility.

\textbf{Execution mode}: Sequential vs. concurrent, as described above.

Each configuration runs 10 times, and we report mean $\pm$ standard deviation to ensure statistical robustness. Our hardware platform is an NVIDIA GPU with CUDA 12.x, running on Linux with GCC 13.

\subsection{Performance Metrics}

We measure the following metrics for each experiment:

\textbf{Latency metrics}:
\begin{itemize}
\item \emph{Average wait time}: Mean time tasks spend waiting in the ready queue
\item \emph{Maximum wait time}: Worst-case waiting time across all tasks
\item \emph{Average execution time}: Mean GPU kernel execution time
\item \emph{Turnaround time}: Wait time + execution time
\item \emph{Makespan}: Total time from first task submission to last task completion
\end{itemize}

\textbf{Throughput}: Tasks completed per second, computed as total task count divided by makespan.

\textbf{Fairness}: Jain's fairness index applied to per-workload throughput (or inverse slowdown).

\textbf{GPU utilization}: Percentage of makespan spent executing kernels (execution time $\div$ makespan $\times$ 100\%).

\textbf{Slowdown metrics}:
\begin{itemize}
\item \emph{Average slowdown}: Mean ratio of shared execution time to solo execution time per workload
\item \emph{Maximum slowdown}: Worst-case slowdown across workloads
\item \emph{Weighted slowdown}: Slowdown weighted by workload size
\end{itemize}

Per-workload breakdown allows us to identify which workloads benefit or suffer under each scheduler, revealing fairness issues masked by aggregate statistics.

\subsection{Scheduler Comparison and Tradeoffs}

Different schedulers make distinct tradeoffs between latency, fairness, and throughput. Figure~\ref{fig:config_impact_concurrent} visualizes scheduler performance across key metrics for concurrent execution.

\textbf{FIFO} provides a neutral baseline. It achieves moderate throughput and makespan without favoring any workload. On imbalanced\_4 with batch=128 concurrent, FIFO completes in 179.6ms with 9,784 tasks/s throughput and 70\% GPU utilization.

\textbf{Priority scheduling} minimizes latency for high-priority tasks at the cost of fairness. On the imbalanced\_4 workload, Priority reduces high-priority task slowdown (wl 0: 42$\times$ vs. 38$\times$ for FIFO, wl 2 large circuit: 12,738$\times$ vs. 51,128$\times$ for FIFO) by aggressively scheduling high-priority work first. \textbf{Dependency-aware schedulers} exploit task graph structure with varying results:

\begin{itemize}
\item \textbf{HighFanout} prioritizes tasks with many dependents to unlock parallelism. This yields the best fairness among dependency-aware policies on imbalanced workloads (wl 1: 3,010$\times$ vs. 17,000+$\times$ for others), reducing starvation of large circuits. However, it achieves only 65\% GPU utilization due to conservative batching.

\item \textbf{CriticalPath} minimizes makespan by prioritizing the longest dependency chain. However, it sacrifices fairness (wl 1: 17,491$\times$ slowdown) and achieves poor throughput (5,014 tasks/s, worst among all schedulers) because tasks off the critical path wait excessively.

\item \textbf{LevelAware} groups tasks by dependency level. It achieves high GPU utilization (94\%) and moderate throughput (6,786 tasks/s) but suffers the worst fairness (wl 1: 137,277$\times$ slowdown), indicating extreme starvation of certain levels.

\item \textbf{Hybrid} combines priority with dependency-awareness, yielding high GPU utilization (98\%) but the longest makespan (478ms) as complex scheduling logic increases dispatch overhead.
\end{itemize}

\subsection{Summary of Tradeoffs}

Our evaluation reveals several fundamental tradeoffs in GPU scheduling:

\textbf{Fairness vs. Workload Balance}: Balanced workloads enable fair resource sharing (Jain's index $>$0.99) regardless of scheduler, while imbalanced workloads cause fairness degradation (Jain's index $\sim$0.67) as small tasks complete quickly while large tasks suffer extreme slowdowns.

\textbf{Priority vs. Fairness}: Priority scheduling minimizes latency for high-priority tasks (12,738$\times$ vs. 51,128$\times$ slowdown for large circuits under Priority vs. FIFO) but inherently sacrifices fairness by design.

\textbf{Dependency-Awareness vs. Simplicity}: Dependency-aware schedulers can improve makespan (CriticalPath) or fairness (HighFanout) by exploiting graph structure, but add complexity and may perform poorly on graphs that don't match their assumptions (e.g., LevelAware's 137,000$\times$ slowdown).

\textbf{Utilization vs. Makespan}: Concurrent execution achieves 65--99\% GPU utilization vs. 6--9\% for sequential, but increases makespan due to coordination overhead. The choice depends on whether maximizing instantaneous throughput (sequential) or sustained utilization (concurrent) is more important.

These tradeoffs guide policy selection: FIFO for simplicity and fairness on balanced workloads, Priority for latency-sensitive applications willing to sacrifice fairness, HighFanout for imbalanced workloads requiring better fairness, and concurrent execution for sustained high GPU utilization.

\section{Conclusion}
\label{sec:conclusion}

We have presented a comprehensive empirical study of latency, fairness, and throughput tradeoffs in non-preemptive GPU scheduling. Through implementation and evaluation of six scheduling policies (FIFO, Priority, HighFanout, CriticalPath, LevelAware, Hybrid) across diverse workload configurations and execution modes, we quantify fundamental tradeoffs that guide policy selection in shared GPU environments.

Our key findings demonstrate that:

\textbf{Workload balance dominates fairness}: Balanced workloads enable near-perfect fairness (Jain's index $>$0.99) regardless of scheduler, while imbalanced workloads expose scheduler-dependent fairness degradation to 0.67--0.81. The 169$\times$ size disparity in our most imbalanced workload creates slowdown ratios ranging from 37$\times$ for small circuits to over 137,000$\times$ for large circuits under certain schedulers.

\textbf{Priority scheduling trades fairness for latency}: Priority-based policies successfully minimize latency for high-priority tasks, reducing slowdowns from 51,000$\times$ to 12,700$\times$ for large high-priority circuits. However, this comes at the cost of inherent unfairness and potential starvation of low-priority work.

\textbf{Dependency-aware policies offer mixed results}: Exploiting task graph structure can improve specific metrics (HighFanout reduces large-circuit slowdowns to 3,010$\times$, CriticalPath minimizes makespan), but these policies perform poorly when graph characteristics don't match their assumptions. The complexity of dependency-aware scheduling does not universally outperform simpler FIFO or Priority approaches.

\textbf{Concurrent execution is essential for utilization}: Sequential batch dispatch achieves only 6--9\% GPU utilization due to CPU launch overhead, while concurrent multi-stream execution reaches 65--99\% utilization. Although sequential execution can achieve higher instantaneous throughput for small task sets due to shorter makespan, concurrent execution is necessary for sustained GPU productivity in continuous workload scenarios.

These findings provide concrete, data-driven guidance for practitioners designing shared GPU systems. FIFO scheduling suffices for balanced workloads requiring simplicity and fairness. Priority scheduling is appropriate when latency-sensitive applications must be protected at the cost of fairness. For imbalanced workloads requiring better fairness than Priority provides, HighFanout offers a middle ground. Concurrent execution should be preferred in all cases where sustained GPU utilization matters more than minimizing single-run makespan.

\subsection{Future Work}

Several directions extend this work:

\textbf{Hardware-level profiling}: While we attempted to profile GPU performance counters (memory bandwidth, cache hit rates, warp occupancy) to understand utilization bottlenecks, the profiling overhead proved prohibitive for our large-scale experiments. Future work could use sampling-based profiling or hardware performance monitoring units to characterize scheduler behavior at finer granularity without excessive runtime overhead.

\textbf{Adaptive scheduling}: Our schedulers use static policies, but workload characteristics evolve during execution. An adaptive scheduler could dynamically switch policies based on observed fairness, utilization, or latency metrics, combining the strengths of multiple approaches.

\textbf{Beyond logic simulation}: While ISCAS-85 circuits provide realistic task graphs with diverse structure, evaluating schedulers on additional domains (machine learning inference, scientific computing, graphics rendering) would test generalizability and reveal domain-specific tradeoffs.

\textbf{Multi-GPU scheduling}: Modern systems increasingly use multiple GPUs. Extending our schedulers to multi-GPU environments introduces new dimensions (inter-GPU communication, NUMA effects, load balancing) that may shift the tradeoff landscape.

\textbf{Preemption and virtualization}: Current GPUs remain fundamentally non-preemptive, but emerging GPU architectures and virtualization layers are exploring preemption mechanisms. If preemptive GPUs become practical, revisiting these tradeoffs with preemption-aware policies would be valuable.

Our work establishes empirical foundations for understanding GPU scheduling tradeoffs, enabling informed decisions in the design of shared GPU systems and motivating future research into adaptive, workload-aware scheduling policies.
